## 맥락

주문 계산 규칙을 테스트하려는데 데이터베이스와 결제 게이트웨이가 함께 떠야 했습니다.
도메인 클래스가 JPA 애노테이션과 HTTP 클라이언트를 직접 참조하고 있었기 때문입니다.

규칙 하나를 확인하는 테스트가 수 초씩 걸렸고, 그래서 아무도 규칙에 대한 테스트를
잘 쓰지 않았습니다.

## 결정

의존 방향을 도메인 쪽으로만 흐르게 합니다.

- `domain` 은 다른 패키지를 import 하지 않습니다. 프레임워크도 포함해서입니다.
- 도메인이 밖을 필요로 하면 **포트**(인터페이스)를 도메인 안에 정의하고,
  `infrastructure` 가 그것을 구현합니다.
- `web` 은 `application` 을, `application` 은 `domain` 을 압니다. 역방향은 없습니다.

## 결과

**얻는 것** — 도메인 규칙 테스트에 스프링도 DB도 필요 없습니다. 영속성이나 외부 API를
바꿔도 도메인은 그대로입니다.

**치르는 대가** — 포트와 어댑터라는 간접 층이 하나 늘어납니다. 저장 하나를 추가할 때
인터페이스와 구현을 함께 만들어야 하고, 처음 오는 사람에게는 "왜 두 번 쓰지"로 보입니다.

`패키지 의존 구조` 다이어그램에서 `domain` 에 나가는 화살표가 하나도 없는 것이
이 결정입니다.
